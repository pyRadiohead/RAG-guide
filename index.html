Part 1 — RAG 101

What is RAG, and why bother?

A language model knows a lot, but it does not know your documents, and it makes things up when unsure. RAG fixes both by letting the model look things up before it answers.

Closed-book

Ask the model directly. It answers from memory — fast, but it can confidently invent facts (a "hallucination"), and it has never seen your private or recent data.

Open-book (RAG)

First retrieve the few most relevant passages from a library, then hand them to the model and ask it to answer using only those. Grounded, checkable, updatable.

The exam analogy. Closed-book = answer from memory. RAG = an open-book exam: the trick is no longer knowing everything, it is finding the right page fast. Most of the engineering in RAG is about that search — not the writing.

Two ways to "find the right page"

Every RAG system searches the library two complementary ways, because each catches what the other misses.

BM25 · keyword

Sparse / lexical. Matches the actual words. Great for exact terms, names, jargon, acronyms — "Kubernetes", "ФОП", "React 19". Blind to synonyms: it does not know "salary" ≈ "зарплата".

Dense · meaning

Dense / semantic. Turns text into a list of numbers (an embedding) so that similar meanings sit close together. Finds the right passage even with different words — but can drift on exact terms.

Embedding, in one line. A model reads a passage and outputs a point in a high-dimensional space (here: 3072 numbers). "Closer points = more alike." Searching becomes geometry: find the nearest neighbours to the question's point.

Then: fuse, diversify, rerank, extract

Two ranked lists are not an answer. Four more steps turn them into one — each has its own interactive demo further down:

Part 2 — The case study

A real competition on DOU.ua

The UA Agent Builder Lab challenge: answer 364 questions over 3851 Ukrainian tech articles. Each answer needs the source URLs and three extracted values. One scorer judged both.

How you were scored

A single number combined two jobs — finding the right pages, and reading the right values off them:

combined = 0.7 · F1urls  +  0.3 · claim_acc
F1 (urls)

Did the URLs you returned match the ground-truth set? Rewards both precision (no junk) and recall (nothing missed).

claim_acc

Did the three values you extracted (after normalising numbers & text) match? e.g. 1,000 → 1000, 3.5% stays 3.5%.

The precision leak

The single biggest score jump came not from a better model, but from returning fewer URLs. Here is why — drag the slider.

The clue. In this dataset the correct answer almost always cites exactly 3 URLs (median 3, max 4). If you return 10, seven are guaranteed wrong — your precision, and therefore F1, collapses. More retrieval looked safer; it was a trap.

Public vs. private? Kaggle splits the test set into two hidden halves. The public score (one half) is shown live during the contest; the private score (the other half) decides the final ranking. Each half is small, so both wobble — never overfit to the public number.
The wall we hit

One ceiling limits everything: recall@3 = 0.61

After fixing precision, both scores stalled against the same wall. If the article holding the answer never reaches the top 3, you cannot cite it and you cannot read its value. 39% of correct articles never make the top 3 — so 39% is lost to both F1 and claim accuracy at once.

The cheap win

Decoupling. Let the extractor read the top 5 passages (recall@5 = 0.75) but still submit only the top 3 URLs. F1 is unchanged (same top 3), yet the answer's article is more often present to read — claim absence on the hardest field fell 41.5% → 27.5%.

The model swap

Extraction is the claim lever. Keep retrieval on Gemini, route only the final answer-extraction to Claude Sonnet 4.6. Claim accuracy rose 0.359 → 0.447 → ~0.50 with no change to retrieval.

Lesson. Past this point, more prompt-engineering on extraction yields little — the remaining gain needs better retrieval (getting the right article into the top 3). That is the hard, unsolved wall.

What did NOT work

Dead ends — the things that lost

For one win there were eight measured losses. Writing them down matters: each closes a tempting avenue so the next person does not pay to re-learn it. Every number is a controlled A/B against the same baseline — green up means it helped, red down means it hurt.

The pattern behind the reranker failures. This metric rewards which articles are the cited sources — a topical association that dense embeddings capture directly. Rerankers optimise a different question, which passage best answers the query. On a source-attribution task that is the wrong objective, so a relevance reranker adds noise instead of signal. The lone exception: the in-pipeline LLM rerank, which earns its keep only by undoing MMR's diversification — a different job from the isolated rerankers above.
